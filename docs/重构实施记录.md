# ChatHub Desktop 重构实施记录

## 1. 文档目的

本文档用于完整记录本次 `refactor/feature-split` 分支上的重构工作，目标是：

1. 从头到尾记录重构背景、痛点、实施步骤与结果。
2. 明确哪些能力属于“禁止回归项”，尤其是 Google 登录相关的 UA 伪装能力。
3. 为后续继续重构提供连续上下文，避免再次出现“重构到一半，旧结构和新结构并存”的情况。

## 2. 本次重构开始前的状态

重构开始前，项目已经回退到一个稳定可运行版本。该版本的主要问题并不是功能不可用，而是结构性问题越来越明显。

### 2.1 当时的主要痛点

1. `src/main.ts` 体积过大，同时承担了应用启动配置、托盘创建、主窗口创建、菜单处理、快捷键注册、模型同步、应用事件注册等多种职责。
2. 文件结构按历史演进自然生长，职责边界不清晰，阅读成本较高。
3. 配置读写逻辑分散在多个模块中，很多文件直接调用 `readUserSetting` / `writeUserSetting`，导致修改配置结构时影响面过大。
4. 代码风格不够统一，有的模块走工厂注入，有的模块直接操作工具函数，演进方向不够一致。

### 2.2 重要背景

在更早一轮未完成的重构中，曾经出现过“局部 `windowManager` 和全局 `windowManager` 并存”的问题，导致运行时状态不一致。为避免继续在半重构状态上修补，本次先回到稳定基线，再重新分阶段重构。

## 3. 重构总原则

本次重构遵循以下原则：

1. 先收拢职责，再调整目录。
2. 先瘦身 `main.ts`，再逐步拆服务层。
3. 每一步都必须保证行为不变，避免功能回归。
4. 不引入新的核心全局状态。
5. 对“Google 登录绕过 / UA 伪装”相关功能保持零破坏。

## 4. 禁止回归项

这部分能力被明确视为本次及后续重构中的保护项，不允许被误删、弱化或替换。

### 4.1 启动参数伪装

当前关键配置位于：

- `src/core/app-config.ts`
- 原始逻辑来源于旧版 `src/main.ts`

1. `ignore-certificate-errors`
2. `disable-blink-features=AutomationControlled`
3. `disable-features=WebGPU,WebAuthn`
4. `disable-quic`

其中 `AutomationControlled` 是 Google / Cloudflare 检测链路中的关键项，本次重构中已经明确保留，不得删除。

### 4.2 WebView 预加载伪装

当前关键文件：

该文件中仍然保留了以下伪装逻辑：

2. 移除 `navigator.webdriver`。

4. 模拟 `navigator.languages`。

虽然当前 `webview-preload.ts` 中仍保留了硬编码 UA 的实现说明，但本轮重构没有移除该常量，也没有改动与 UA 伪装相关的整体设计。

## 5. 分支处理记录

为了保证后续重构历史干净，本次先对 `refactor/feature-split` 分支做了清理。

### 5.1 已执行操作

1. 删除本地旧分支 `refactor/feature-split`
2. 基于稳定版本重新创建本地 `refactor/feature-split`
3. 删除远程旧分支 `origin/refactor/feature-split`

旧分支里带有上一轮“半重构”历史，继续叠加开发会混淆上下文，也容易把错误结构继续带进新方案。重建分支后，后续每个阶段的提交都更清晰。

## 9. 第三阶段重构：瘦身 tray-context-menu 上下文

### 9.1 阶段目标

第三阶段的重点不是继续移动文件，而是先压缩 `tray-context-menu` 与各 handler 之间的传参噪音。

在第二阶段结束时，`tray-context-menu` 虽然已经不再直接负责所有业务实现，但它传递给 handlers 的 `options` 仍然比较胖，里面混有：

1. `windowManager`
2. `getMainBrowserWindow`
3. `setMainBrowserWindow`
4. `withBrowserWindow`
5. shortcut 状态读写
6. 更新管理器
7. 菜单就绪状态

这些字段里有一部分对菜单层并没有直接意义，更多是历史兼容产物。

### 9.2 第三阶段的核心思路

这一阶段采取了一个比较保守但有效的策略：

1. 不改业务行为。
2. 不推翻已有 handlers。
3. 先把传给菜单与 handlers 的运行时上下文变得更语义化。

也就是说，不再让 handlers 拿到整块 `windowManager` 再自己做各种 fallback，而是直接给它们更聚焦的能力接口。

### 9.3 第三阶段具体调整

#### `src/tray-context-menu.ts`

在该文件中，对 `TrayContextMenuOptions` 做了重构：

1. 新增 `TrayMenuUrls` 类型，单独承接模型 URL 配置。
2. 删除了 `windowManager` 字段。
3. 删除了 `getMainBrowserWindow()`。
4. 删除了 `setMainBrowserWindow()`。
5. 保留 `withBrowserWindow()`。
6. 新增 `getBrowserWindow()`。
7. 新增 `toggleWindow()`。
8. 新增 `setAlwaysOnTop()`。

这样做的目的，是让菜单上下文更像“动作能力集合”，而不是“把底层对象整块透传”。

#### `src/core/bootstrap.ts`

在 bootstrap 中，相应调整了传入 `setupTrayContextMenu()` 的上下文：

1. 使用 `getBrowserWindow: () => windowManager.getMainBrowserWindow()`
2. 使用 `toggleWindow: () => windowManager.toggleWindow()`
3. 使用 `setAlwaysOnTop: (alwaysOnTop) => windowManager.setAlwaysOnTop(alwaysOnTop)`

同时去掉了不再需要的 `setMainBrowserWindow` 透传。

#### `src/handlers/utils.ts`

`getAvailableBrowserWindow()` 被改为只依赖一个 `getBrowserWindow()` 能力，而不再需要：

1. `windowManager`
2. `getMainBrowserWindow`

这让窗口获取逻辑对调用方更透明，也减少了 handler 侧对底层窗口管理器结构的感知。

#### `src/handlers/model-handler.ts`

模型切换逻辑改为：

1. 继续通过 `settings-service` 更新当前模型
2. 直接通过 `options.getBrowserWindow` 获取可用窗口
3. 向窗口发送 `model-changed`

不再需要从上下文中读整块 `windowManager`。

#### `src/handlers/system-handler.ts`

系统操作逻辑做了两处接口收敛：

1. 置顶切换从 `options.windowManager.setAlwaysOnTop()` 改为 `options.setAlwaysOnTop()`
2. 更新检查的窗口获取从“传 windowManager + getMainBrowserWindow”改成直接传 `getBrowserWindow`

#### `src/handlers/shortcut-handler.ts`

这是第三阶段收益最明显的地方之一。

本次做了两件事：

1. 新增了 `registerWindowShortcut()` 这个内部帮助函数
2. 将大量重复出现的“注册快捷键后切换窗口”逻辑统一收口

重构前，这个文件里反复出现如下模式：

1. 读取 `options.windowManager`
2. 调 `getAvailableBrowserWindow(options.windowManager, options.getMainBrowserWindow)`
3. 判空
4. 再调用 `options.windowManager.toggleWindow()`

重构后，这些都收敛成了：

1. `registerWindowShortcut(shortcut, options)`
2. 内部通过 `options.getBrowserWindow()` 和 `options.toggleWindow()` 统一处理

这一步虽然没有改变业务能力，但明显减轻了重复代码量和阅读负担。

### 9.4 第三阶段的直接收益

这一阶段完成后，有几个非常实际的收益：

1. `tray-context-menu` 的上下文接口更接近“菜单操作需要什么”，而不是“底层现在有什么”。
2. handlers 对 `windowManager` 具体结构的耦合进一步下降。
3. shortcut 相关逻辑的重复注册代码减少。
4. 后续如果继续抽 `tray action service`，会更容易落地。

### 9.5 第三阶段验证结果

执行了 `pnpm run lint`。

结果：

1. 没有新增 error。
2. warning 依然保持在原有的 13 个存量问题。
3. 当前第三阶段改动没有引入新的静态检查风险。

## 10. 第四阶段重构：拆分 tray 菜单状态与动作绑定

### 10.1 阶段目标

第三阶段结束后，`tray-context-menu.ts` 已经瘦掉了一部分上下文，但这个文件仍然同时承担了三种职责：

1. 读取菜单状态
2. 绑定点击动作
3. 拼接 Electron 菜单模板

第四阶段的目标，就是把这三件事再往外拆一步，让 `tray-context-menu.ts` 更接近纯描述层。

### 10.2 第四阶段的拆分思路

这一阶段遵循的策略是：

1. 不改变现有菜单行为。
2. 不改 handlers 的业务逻辑。
3. 先拆出“状态提供者”和“动作绑定器”。

这样一来，`tray-context-menu.ts` 自己就不需要：

1. 直接读取 setting
2. 直接拼装各种 handler 调用
3. 在一个文件里同时处理 UI 状态和业务动作

### 10.3 本阶段新增文件

新增文件：

1. `src/handlers/tray-menu-state.ts`
2. `src/handlers/tray-menu-actions.ts`

### 10.4 本阶段具体拆分

#### `src/handlers/tray-menu-state.ts`

新增了 `getTrayMenuState()`，专门负责从 `settings-service` 中读取 tray 菜单渲染所需的状态。

当前收口的状态包括：

1. `currentModel`
2. `alwaysOnTop`
3. `isAutoLaunchEnabled`
4. `menuLanguage`

这样做之后，`tray-context-menu.ts` 不需要自己再去关心 setting 对象的具体结构。

#### `src/handlers/tray-menu-actions.ts`

新增了 `createTrayMenuActions()`，负责把 menu 层要用到的 click 行为统一封装起来。

当前封装的动作包括：

1. 模型切换
2. 置顶切换
3. 设置快捷键
4. 设置代理
5. 切换开机自启
6. 切换菜单语言
7. reload
8. 检查更新
9. quit

这一层的作用，是把“菜单点击后该调谁”集中起来，避免 `tray-context-menu.ts` 自己散落着拼接 handler。

#### `src/tray-context-menu.ts`

这一文件现在的职责更纯了：

1. 读取 `getTrayMenuState()`
2. 创建 `createTrayMenuActions()`
3. 使用状态与动作拼装 `Menu.buildFromTemplate()`

也就是说，它现在更像一个真正的“菜单描述器”。

### 10.5 第四阶段的收益

这一步完成后，tray 这一层出现了更清晰的三段结构：

1. 状态：`tray-menu-state.ts`
2. 动作：`tray-menu-actions.ts`
3. 视图描述：`tray-context-menu.ts`

直接收益包括：

1. `tray-context-menu.ts` 阅读负担更低。
2. 菜单状态与菜单行为不再揉在一起。
3. 后续如果继续抽成 `tray-menu-builder` 或 `tray action service`，会更顺。
4. 新增菜单项时，开发者更容易判断代码应该落在哪一层。

### 10.6 第四阶段验证结果

执行了 `pnpm run lint`。

结果：

1. 没有新增 error。
2. warning 仍保持在原有的 13 个存量问题。
3. 本阶段拆分没有引入新的静态检查风险。

## 11. 第五阶段重构：下沉 tray 业务动作到 service

### 11.1 阶段目标

第四阶段完成后，`tray-context-menu.ts` 已经拆成了“状态 + 动作 + 模板”三段结构，但其中的 `tray-menu-actions.ts` 仍然更像一个组合器：

1. 它主要把菜单动作继续转发给旧的 `model-handler.ts`
2. 它主要把系统类动作继续转发给旧的 `system-handler.ts`

这意味着“菜单层已经变轻”，但“真正的业务动作层”还没有完全稳定。

第五阶段的目标，就是把 tray 菜单里那些更偏业务语义的动作继续下沉到 service，让：

1. handler 更聚焦于带有交互流程的桥接逻辑
2. service 更聚焦于业务动作本身

### 11.2 本阶段具体调整

#### 新增 `src/services/tray-action-service.ts`

这一文件收口了 tray 菜单中更偏业务语义的动作，包括：

1. 模型切换
2. 置顶切换
3. 开机自启切换
4. 菜单语言切换
5. reload 当前模型
6. 检查更新
7. 退出应用

这些动作原本分散在：

1. `src/handlers/model-handler.ts`
2. `src/handlers/system-handler.ts`

现在统一进入 `tray-action-service.ts`，由 service 负责实际业务执行。

#### `src/handlers/tray-menu-actions.ts`

这一文件现在不再直接依赖：

1. `model-handler.ts`
2. `system-handler.ts`

而是改为依赖 `tray-action-service.ts`，只负责：

1. 组合 tray action service
2. 组合仍然需要交互流程的 shortcut / proxy handlers

这样一来，它的定位就更清晰了：

1. 对简单业务动作，直接交给 service
2. 对复杂交互动作，继续交给 handler

## 19. 第九阶段优化：用 ready signal 替代 handler 内部轮询等待

### 19.1 问题背景

在 `src/handlers/proxy-handler.ts` 和 `src/handlers/shortcut-handler.ts` 中，都曾存在一段相同的等待逻辑：当 menubar 尚未 ready 时，通过固定次数的 `for` 循环配合 `delay(100)` 进行轮询等待。

这种写法短期内可以工作，但结构上存在几个问题：

1. handler 自己承担了启动时序控制，职责偏重。
2. `20 * 100ms` 属于魔法数字，语义不够明确。
3. 两个文件重复实现，后续容易复制到更多位置。
4. 等待结束后没有一个清晰的“成功 ready / 超时未 ready”的抽象结果。

### 19.2 本次优化原则

本次不再让 handler 猜测 menubar 什么时候 ready，而是改为：

1. 启动层负责发布 ready 信号。
2. 调用层按需等待 ready 信号。
3. 保留超时兜底，避免出现无限等待。

也就是说，从“轮询式等待”切换为“事件/信号式等待”。

### 19.3 实施内容

#### 新增 ready signal 工具

新增文件：

1. `src/utils/ready-signal.ts`

这个工具提供三个能力：

1. `isReady()`
2. `markReady()`
3. `waitUntilReady(timeoutMs?)`

这样后续任何“初始化完成后再执行”的场景，都可以复用这套模式，而不必继续写 `delay` 轮询。

#### 调整 bootstrap

在 `src/core/bootstrap.ts` 中：

1. 取消了原先的局部布尔变量式 `isMenubarReady` 管理方式。
2. 改为创建 `menubarReadySignal`。
3. 在 tray context 初始化时向下传递：
   - `isMenubarReady`
   - `waitForMenubarReady`
4. 在启动流程完成后，显式调用 `markReady()`。

这样 ready 的“产生方”回到了启动层，语义是正确的。

#### 扩充 tray context 能力

在 `src/tray-context-menu.ts` 中，为 `TrayContextMenuOptions` 新增：

1. `waitForMenubarReady(timeoutMs?: number): Promise<boolean>`

这意味着 handler 不仅能判断“当前是否 ready”，还可以明确表达“请等待 ready，直到超时”。

#### 收口 handler 侧的等待逻辑

在 `src/handlers/utils.ts` 中新增：

1. `ensureMenubarReady()`

这个工具函数负责：

1. 先走快速判断。
2. 再等待 ready signal。
3. 若超时未 ready，则统一弹出 `appNotReadyMessage`。

随后：

1. `src/handlers/proxy-handler.ts` 删除本地 `delay()` 与轮询逻辑。
2. `src/handlers/shortcut-handler.ts` 删除本地 `delay()` 与轮询逻辑。
3. 两者统一改为调用 `ensureMenubarReady()`。

### 19.4 这样改的收益

这次改动虽然不大，但它解决的是“结构质量”问题：

1. 启动时序控制回归启动层，职责更清晰。
2. handler 只关心自己的交互流程，不再内嵌启动轮询。
3. 去掉重复魔法数字，代码可读性更好。
4. 后续如果还有其他需要依赖 menubar ready 的交互入口，可以直接复用这套 signal + ensure 模式。

### 19.5 对现有功能的影响说明

本次仅优化了 menubar ready 的等待方式，没有改变这些既有能力：

1. 代理设置保存与应用逻辑。
2. 快捷键录入、恢复、重置逻辑。
3. tray 菜单行为。
4. UA 伪装能力、Google 登录绕过相关链路、`AutomationControlled`、`webview-preload.ts`。
